
## 3. Схема данных: почему именно так

### `leads` — заявки
Содержимое формы лежит в JSON-поле `payload`, а `name` и `contact` вынесены отдельными колонками.
Логика простая: по имени и контакту менеджер ищет постоянно, поэтому они индексируются как обычный текст.
Всё остальное меняется от формы к форме — гонять миграции под каждую новую галочку глупо.

### `consents` — журнал согласий
Отдельная таблица, а не поля внутри заявки. Причина юридическая: по 152-ФЗ ст. 9 ч. 3
оператор обязан **доказать** получение согласия. Заявку можно удалить по сроку,
а запись о согласии живёт дольше. Если положить согласие в `leads`, оно умрёт вместе с лидом.

### `files` — резюме
На диске лежит файл под именем-UUID, в базе — метаданные. Оригинальное имя сохраняется в `original_name`.
По прямой ссылке файл не отдаётся: единственный путь к нему — через авторизованную ручку (пока не сделана, см. п. 6).

### `sessions`
Хранится **хеш** токена, а не токен. Утечка базы не даёт войти по чужим сессиям — восстановить токен из хеша нельзя.

### `texts`
Черновик и публикация — разные статусы. Маркетолог правит, смотрит, и только потом нажимает «Опубликовать».
Без этого разделения опечатка в тексте уезжает на прод моментально.

## 4. Безопасность: что сделано и почему

| Угроза | Защита | Где |
|---|---|---|
| Подбор пароля | scrypt + лимит 5 попыток в минуту на IP | `admin.mjs`, `index.mjs` |
| Кража токена через XSS | `HttpOnly`, `SameSite=Strict`, `Secure` в проде | `admin.mjs` |
| Перебор форм ботом | Лимит 60 записей в минуту, ловушка по IP-хешу | `index.mjs` |
| Файл-малварь под видом PDF | Проверка магии первых байт, не расширения | `index.mjs` |
| Утечка IP из журнала | Храним `sha256(ip + соль)`, не сам IP | `index.mjs` |
| Раздувание базы мусором | Обрезка `payload` до 100 КБ, лимит тела 12 МБ | `index.mjs` |
| Потеря персданных в HTML | Кабинет статический, данные только через API с сессией | `cabinet.astro` |
| Обход ролей | `requireRole` на каждой ручке, admin проходит везде | `admin.mjs` |

**Чего ещё нет, и это важно знать:**

1. **CSRF-токена нет.** Спасает `SameSite=Strict`, но при добавлении сторонних интеграций нужно вернуться.
2. **Нет двухфакторки.** Для админки с персданными стоит добавить TOTP.
3. **Ограничение частоты в памяти.** За балансировщиком каждый инстанс считает своё — нужен Redis.
4. **Нет журнала действий.** Кто и когда смотрел заявку — не пишется. Для 152-ФЗ полезно.

## 5. SEO: что включить при запуске

Ровно два действия, оба в одном месте:

1. `src/data/site.ts` → `indexable: true`
2. Всё. `robots.txt` пересоберётся сам, карта сайта уже есть.

Дальше руками, вне кода:

- 301-переадресации со старого сайта — список адресов брать из Яндекс.Вебмастера;
- один вариант домена (с www или без), остальные — 301;
- Вебмастер и Search Console: подтвердить, отправить `/sitemap-index.xml`, указать регион.

Проверка перед запуском:

```bash
cd site && npm run build
cat dist/robots.txt                       # должен быть Allow и Sitemap
grep -c '<loc>' dist/sitemap-0.xml        # должно быть больше 0
grep canonical dist/index.html            # должен быть абсолютный адрес
```

## 7. Почему node:sqlite, а не Postgres

Сознательное решение, не лень:

- заявок десятки в месяц, не миллионы;
- одна машина, один инстанс — репликация не нужна;
- ноль зависимостей и ноль администрирования;
- WAL-режим включён, читатели не блокируют писателя.

**Когда менять:** при переходе на несколько инстансов, при росте до тысяч записей в день,
или если заявки нужно отдавать во внешнюю CRM в реальном времени. Схема переносится в Postgres
почти как есть, `node:sqlite` и `pg` работают похоже — переписать придётся только слой запросов.
